プラン制・機能制限・課金の設計

無料プランは無し。7日間の無料トライアル後に有料化。シート課金（基本料＋ユーザー追加ごとの従量）で、上位プラン（Pro）は「空車定期登録」と「荷物の複数日程一括」を解放。課金はテナント（会社）単位・Stripe カードのみ。土台は既存（tenancy.feature_enabled() が features→env の順で判定、両機能は既にゲート済み）。Stage 1（マルチテナント）に載せる前提。

1. プラン（2階層・シート課金・7日トライアル）

会社（テナント）ごとに 1 プラン。すべて Stripe カード決済。7日間の無料トライアル後に課金開始。

Standard
¥4,000 / 月（基本）
＋ ユーザー追加 ¥2,000 / 人・月
  • ✓荷物登録（Trabox / WebKit 一括）
  • ✓空車登録（単発）
  • ✓成約トラッキング・履歴・失敗タスク再投稿
  • –空車定期登録
  • –荷物の複数日程一括
Pro上位
¥5,000 / 月（基本）
＋ ユーザー追加 ¥3,000 / 人・月
  • ✓Standard の全機能
  • ✓空車定期登録（毎週/隔週/毎日/毎月・初期登録回数）
  • ✓荷物の複数日程一括（最大5日程）
  • ✓履歴から再登録（過去の荷物/空車を元にワンクリックで再投稿）
プラン基本料/月ユーザー追加/月例: 3ユーザーPro機能
Standard¥4,000¥2,000 / 人¥4,000 + ¥2,000×2 = ¥8,000×
Pro¥5,000¥3,000 / 人¥5,000 + ¥3,000×2 = ¥11,000○ 定期＋複数日程

※「ユーザー追加」= 基本料に1人目（アカウント料）を含み、2人目以降を課金（確定）。Stripe のシート quantity = 有効ユーザー数 − 1。

Standard が Pro 機能を開こうとした場合：UIは「Proにアップグレード」表示、APIは 403（既存の _require_feature / FEATURE_MULTIDATE ゲートを流用）。Pro→Standard へ下げたら既存の定期ルールを自動停止（再アップグレードで復帰）。トライアル終了で未課金なら投稿系をロック。

2. データモデル（tenants に課金を集約）

Stage 1 の tenants ドキュメントへ課金フィールドを追加。features は plan から導出。

新規フィールド プランから自動導出
🏢 tenants（課金拡張） Stage1 + 課金
  • #id / name
  • ◆plan"standard" | "pro"
  • ◆features{recurring, multidate}（plan由来）
  • ◆seats課金対象ユーザー数（=有効users数）
  • ◆stripe_customer_idStripe 顧客ID
  • ◆stripe_subscription_idサブスクID
  • ◆subscription_statustrialing/active/past_due/canceled
  • ◆trial_endトライアル終了(7日)
  • ◆current_period_end次回更新日
既存の webkit_apikey もここ（Stage 1）。features は「plan→features マップ」で常に上書き＝プランと機能が食い違わない。seats は tenant の有効ユーザー数と常に同期。

3. 機能ゲートの効き方

1本の関数で判定。UIと API の両方で同じ真偽を使う（既存の仕組みを踏襲）。

アクセス→ tenant.plan→ plan→features マップ→ feature_enabled("recurring"/"multidate")→ UI表示 / API許可 or 403

4. 課金フロー（Stripe 採用）

Stripe Checkout（ホスト型決済）＋ Customer Portal（解約/カード変更）＋ Webhook。自前の決済UI・カード保持はしない（PCI負担を回避）。プロバイダ非依存の抽象化層を1枚挟み、将来 Pay.jp へ差し替え可能に。

操作フロー
加入（トライアル開始）テナント管理者がプラン選択→ Checkout（カード登録）→ 7日トライアル開始（trialing）。Webhook で tenant.plan/status/trial_end 反映。トライアル終了で自動課金。
更新・失敗毎月自動課金。失敗は past_due Webhook→猶予表示。回復で active に戻る（dunningはプロバイダ任せ）。
解約・変更顧客ポータル（ホスト型）で解約/カード変更→ Webhook で status/period_end 反映。期末までは Pro 維持→以降 free。
整合性状態の正は Webhook（署名検証・冪等）。画面表示は tenants の保存値を読むだけ。取りこぼしは定期照合で補正。
RevenueCat はモバイルアプリ内課金(IAP)用のため今回のWebカード課金では非採用。将来ネイティブアプリのIAPを出す時に別途検討。

Stripe でのシート課金の作り方

要素Stripe での表現
基本料Standard/Pro それぞれに「基本料」Price（¥4,000 / ¥5,000・licensed・数量1）。
ユーザー追加Standard/Pro それぞれに「シート」Price（¥2,000 / ¥3,000・per-seat licensed）。subscription item の quantity = 有効ユーザー数 − 1（1人目は基本料に含む）。
ユーザー増減ユーザー発行/削除（Stage1のowner操作）に連動して quantity を更新→ Stripe が日割り(proration)で自動調整。
7日トライアルサブスク作成時に trial_period_days = 7。trialing 中は満額機能、終了で課金開始。未決済なら past_due→ロック。
プラン変更Standard⇄Pro は基本料/シートのPrice差し替え（proration）。features は plan から即再導出。
カードのみCheckout の payment_method_types=['card'] でカード限定。

5. 実装フェーズ

課金はテナントに紐づくため、Stage 1 が前提。段階的に。

1

Stage 1：マルチテナント

tenants コレクション＋role（owner/member）＋クエリのテナント絞り。既存レコードは "takeuchi" テナントへ流用（設計図は別紙）。

2

プラン＆機能ゲート（課金なしで先行）

tenant.plan→features、Pro機能ロック表示＋API403、無料/Pro切替は当面フラグ手動。ここまでで「制限UI」は完成・検証できる。

3

課金連携（Stripe）

Stripe Checkout / Customer Portal / Webhook（署名検証・冪等）→ subscription_status で plan 自動更新。Secret は Secret Manager、Webhook は署名シークレットで検証。

4

運用

請求書/領収書（プロバイダ発行）・解約導線・past_due 表示・売上ダッシュボード（任意）。
