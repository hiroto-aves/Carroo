マルチテナント化：ロールとDB構成

外販に踏み切る場合の設計案。現状（Stage 0）は「テナント＝竹内運送1社固定・is_admin の boolean 1枚」。Stage 1 では会社（テナント）を第一級の存在にし、ロールを2階層＋運営者に分けます。既存レコードは tenant_id を持たせ済みなので、土台は入っています。

1. ロール階層

運営者（あなた）＝テナント横断。各社の中は「管理者」と「一般」の2階層。

SUPER ADMIN全テナント横断

運営者（Carroo 側 = あなた）

  • テナントの発行・停止・課金設定（features / WebKit apikey）
  • 全社データの閲覧（サポート対応・障害調査）
  • テナント管理コンソール /ops に入れる唯一のロール
TENANT ADMIN自社内のみ

会社の管理者（例：竹内運送の管理担当）

  • 自社ユーザーの発行・削除（今の /admin/users 相当）
  • 自社の全案件・空車を横断表示／データ整理
  • 自社の連絡先・WebKit担当者IDなどの初期設定
MEMBER自分の担当分

一般ユーザー（現場の配車担当）

  • 荷物・空車の登録／変更／取下げ、成約マーク
  • 既定は自分が登録した案件のみ表示。自社内共有のON/OFF は tenant admin だけが切替可（member 側に切替UIは出さない・APIも 403）
  • ユーザー管理・課金設定には触れない

いまの is_admin=true ⟶ role="owner" に移行、is_admin=false ⟶ role="member"。運営者は別フラグ is_super=true。

2. DB構成（Firestore コレクション）

緑＝新設／変更。テナントが親、その下にユーザーとレコードがぶら下がる形。物理階層ではなく tenant_id で束ねる（現状の実装方針を継承）。

  • #id"takeuchi"

  • ◆webkit_apikeystring

🏢 tenants 1 ─< users N 👤 users 1 ─< cases / trucks / schedules N 🏢 tenants 1 ─< cases / trucks N（tenant_id で横断集計）

3. アクセス制御の効き方

1本のルールで表現できる：「まず tenant で絞り、次に role で絞る」。

リクエスト→ tenant_id 一致?→ role で許可判定→ member は自分の user_id 分のみ / owner は自社全部 / super は全テナント
操作memberowner（会社管理者）super（運営者）
荷物・空車の登録/変更/取下げ自分の分自社の全件全テナント
一覧・ダッシュボード自分の分（共有ON時のみ自社内も表示）自社の全件全テナント
自社内共有の ON/OFF 切替✕（切替UIなし）◯（このロールだけ）◯
ユーザー発行・削除✕自社ユーザーのみ◯（テナント跨ぎ）
データ整理（完全削除）✕自社のみ◯
課金オプション・apikey 設定✕✕（申込のみ）◯ /ops

4. 現状(Stage 0) → Stage 1 の差分

土台がある分、作るのは主に「tenants コレクション」「role 化」「クエリのテナント絞り」「運営コンソール」。

論点いま（Stage 0）Stage 1
テナントenv DEFAULT_TENANT_ID="takeuchi" 固定tenants コレクションで複数社
ロールis_admin の 2値role = owner / member ＋ is_super
課金オプションenv FEATURE_*（全体一律）tenants.features（会社ごと）
WebKit apikeyenv 共通1本tenants.webkit_apikey（会社ごと）
データの絞り込みtenant_id は保存するが未使用検索/集計を tenant_id で必須フィルタ
管理画面/admin（自社ユーザー）＋ /ops 運営コンソール（テナント発行）
既存アカウントの移行全員 tenant_id="takeuchi"（保存済）最初のテナント＝"takeuchi" を流用。現 is_admin=true→owner／それ以外→member（採番し直さず既存レコードそのまま）
既に済んでいる土台tenancy.current_tenant_id()/feature_enabled() は user・features を優先して読む設計、cases/trucks/schedules は tenant_id 保持済み
